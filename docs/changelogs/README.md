# Changelog 约定（通用）

本约定描述如何组织项目的变更记录。**适用于任意项目**——前端 / 后端、任意语言与框架。各项目按本约定在各自的 `docs/changelogs/` 下落地；新项目可直接复制本文件到其 `docs/changelogs/README.md` 套用。

---

## 1. 组织方式：每次变更一篇深度文档

不使用单文件滚动 changelog。每次**有意义的变更**单独成篇、按日期命名独立文件，便于检索与归档。

- **目录**：`docs/changelogs/`
- **文件名**：`YYYY-MM-DD-<slug>.zh.md`
  - `YYYY-MM-DD`：变更日期
  - `<slug>`：英文短横线小写短语，概括本次变更（如 `token-expiry-guard`、`llm-apikey-env-resolution`）
  - `.zh.md`：中文内容（团队约定中文为主）

示例：`2026-06-27-token-expiry-guard.zh.md`

---

## 2. 文档结构

每篇按以下分节（内容简单的节可省略，但顺序保持不变）：

1. **标题**：一句话概括变更
2. **元信息行**：`> 日期：YYYY-MM-DD | 类型：feat/fix/refactor/chore | 关联代码：\`文件路径\``
3. **1. 背景**：为什么要改、痛点是什么
4. **2. 方案**：怎么解决（可含流程图 / 优先级伪代码）
5. **3. 改动清单**：表格，逐文件列出具体改动
6. **4. 设计决定**：表格，关键决策 + 理由（含备选方案为何不选）
7. **5. 验证**：怎么验证的（测试、手动验证、类型检查等），如实记录
8. **6. 范围（本次未做）**：明确边界，哪些留作后续
9. **7. 配套修复与踩坑**：落地时发现的问题与坑（可选）

---

## 3. 记录边界（什么记 / 什么不记）

**单独成篇记录**（有意义的变更）：
- 新增功能（feat）
- 修复 bug（fix）
- 行为变化 / 破坏性改动
- 显著重构（影响接口或明显改变结构）

**不单独成篇**（琐碎 chore，只在相关深度文档的「范围 / 踩坑」里带过，或直接不记）：
- 删除未使用的变量 / import（dead code 清理）
- 格式调整、注释增删
- 重命名
- 依赖版本升级（无行为变化的）

> **判定原则**：这次变更若会影响他人理解系统、或日后需要回溯「为什么这么做」→ 单独成篇；否则不记。

---

## 4. 内容要求

- **语言**：中文为主，技术术语保留英文
- **写清背景与决策理由**，不只罗列「改了什么」
- **验证部分如实记录**，含失败 / 未覆盖项，不藏问题
- 引用代码用行内代码标注文件路径

---

## 5. 与既有 CHANGELOG.md 的关系

若项目原存在单文件 `CHANGELOG.md`（Keep-a-Changelog 风格），将其作为**历史归档保留**：在文件顶部加归档说明，自切换日起不再追加新条目；新变更一律走本约定的深度文档。
